기획서

왜 이걸 만들어야 하는지, 왜 “모델이 더 좋아지면 해결될 문제”가 아닌지, 그리고 시장에 실제로 어떤 빈틈이 있는지. 측정된 숫자만 씁니다.

대상 기획자 선행 없음 후행 02 설계서

1문제 — 장편은 중반부에서 무너진다

LLM으로 장편을 쓰면 무너집니다. 이건 인상이 아니라 2026년에 측정된 사실이고, 어디서 어떻게 무너지는지까지 나와 있습니다.

마이크로소프트와 SUTD가 2026년 3월에 낸 ConStory-Bench는 8,000~10,000단어 생성물 2,000건에서 일관성 오류를 분류했습니다. 5개 범주 19개 세부 유형이 나왔고, 세 가지 패턴이 반복됐습니다.

패턴 1
사실·시간이 지배한다

문체나 어조 문제가 아닙니다. 엔티티 추적과 시간 추론이 오류의 대부분입니다 — 정확히 타입 그래프가 존재하는 이유입니다.

패턴 2
중반부에 몰린다

사실이 처음 확립되는 지점은 분량의 20~24%, 모순이 나타나는 지점은 34~49%, 밀도는 40~60% 구간에 집중됩니다.

패턴 3
고엔트로피 구간이 위험하다

오류를 품은 문장의 평균 섀넌 엔트로피가 전체 평균보다 12~19% 높습니다. 검증 예산을 어디 쓸지 정하는 신호입니다.

사실 확립과 모순 발생 사이의 평균 간격도 유형별로 나와 있습니다 — 지리 31.0%, 절대시간 29.7%, 기억 25.4%, 수량 23.8%, 핵심규칙 23.4%. 반면 시점(perspective) 오류만 4.7%로, 이것만 국소적이고 나머지는 전부 장거리 문제입니다.

검증되지 않은 메모리는 잡음을 더한다

같은 벤치마크의 CED(1만 단어당 오류 수) 순위에서 메모리 레이어를 붙인 시스템이 안 붙인 것보다 나쁜 경우가 있습니다 — DOME은 1.033으로 순수 GPT-5-Reasoning의 0.113보다 훨씬 나쁩니다. 이것이 이 설계에서 진단 규칙을 결정론으로 먼저 까는 이유입니다.

2컨텍스트를 키워도 해결되지 않는다

2M 토큰이면 된다는 기대는 측정과 맞지 않습니다. 문제는 “안 들어간다”가 아니라 “넣어도 못 쓴다”입니다.

과제 유형측정 조건결과함의
단일 needle 검색 (NIAH)@1M 토큰96–99%“2M 됩니다”라는 마케팅이 나오는 지점
다중 needle 종합 (MRCR v2)@128K 토큰74–93%1M이 아니라 128K에서 이미 깨짐
문자 비일치 추론 (NoLiMa)@32K 토큰12개 중 10개가
단문 성능의 절반 이하		“3장 왼손잡이 ↔ 17장 오른손”이 정확히 이 유형
증거 거리별 임베딩 RAG거리 증가F1 37.1 → 7.4소설은 최대 증거-거리 워크로드

업계 정리로는 프론티어 모델이 멀티홉 작업에 실제로 쓸 수 있는 구간이 광고 컨텍스트의 50~65%입니다. 게다가 소설은 읽기보다 쓰기이고, 출력 한계는 입력과 별개로 훨씬 작습니다. 책 한 권을 한 번에 뱉을 수 없으니 어차피 챕터 단위로 반복해야 하고, 그러면 매 챕터마다 50만 자를 다시 밀어 넣는 건 비용과 지연 면에서 성립하지 않습니다.

그래서

“통째로 읽기”의 실질적 대안은 “잘 만든 요약을 통째로 읽기”입니다. 원문 50만 자 대신 구조화 인덱스 2만 자. 밀도가 높아서 NoLiMa 문제도 거의 안 생깁니다. 그 인덱스를 만들고 유지하는 것이 이 시스템의 본체입니다.

3지렛대는 추출 품질이 아니라 표현이다

이 프로젝트가 성립하는 가장 중요한 근거입니다.

PocketFM이 2026년 7월에 낸 Narrative World Model(NWM)은 서사학 기반 타입 스키마로 소설 메모리를 구성하고 범용 에이전트 메모리와 통제 비교했습니다.

MCP 툴을 get_full_state() 하나로 만들면 안 됩니다. 반드시 의도와 기준 시점을 받아 시드를 랭킹하고 1-hop 타입 이웃으로 확장한 뒤 예산으로 절단하는 조건부 검색 툴이어야 합니다. 설계서의 neighborhood가 이 역할입니다.

빈틈의 정확한 위치

기존 도구는 전부 “무엇이 있는가”는 저장하지만 “작가가 무엇을 약속했고 아직 안 갚았는가”는 저장하지 않습니다. 복선은 본질적으로 시간 제약이 걸린 방향 있는 부채인데, 이걸 데이터로 다루는 도구가 하나도 없습니다.

추상적인 기능 목록 대신, 실제로 어떻게 쓰이는지 세 장면으로 보여줍니다. 예시 작품은 미스터리 「회색 등대」입니다.

6왜 MCP인가

축은 “UI를 만드느냐”가 아니라 “에이전트 루프를 누가 소유하느냐”입니다.

어려운 부분은 어느 쪽으로 가도 똑같습니다. 인덱스·요약·상태 레이어는 자체 앱을 만들어도 만들어야 하고, 컨텍스트 한계도 동일합니다. 그 공통분모를 빼면 남는 차이는 하나 — 컨텍스트 예산 관리와 압축, 툴 호출 루프와 부분 실패 복구, 멀티스텝 계획과 서브에이전트 분업, 스트리밍·취소·재개, 승인·권한, 그리고 가장 어려운 관측과 평가. 이걸 다 만들면 결국 Claude Code를 다시 만드는 것이고, 게다가 움직이는 표적입니다.

이유 1
어려운 부분이 양쪽 다 같다

공통분모를 빼면 차이는 에이전트 루프 하나뿐인데, 그건 몇 달짜리 일입니다. 그동안 소설은 한 줄도 안 써집니다.

이유 2
개인 도구다

자체 개발의 진짜 장점은 UX 통제와 배포인데, 사용자가 한 명이면 둘 다 의미가 없습니다.

이유 3
되돌리기가 비대칭적으로 쉽다

MCP 서버는 잘 정의된 함수 모음입니다. 나중에 Agent SDK로 자체 루프를 얹어도 100% 재사용됩니다. 반대 방향은 버리는 겁니다.

언제 뒤집어야 하는가

에이전트가 툴을 안 부르거나 순서를 틀려서 품질이 들쭉날쭉해질 때. 그때도 전체 재구현이 아니라 훅으로 순서를 박는 것부터 하면 됩니다 — 그것도 같은 MCP 서버 위에서.

7성공의 정의

측정 가능한 것만 씁니다. 셋 다 기존 벤치마크로 잽니다.

지표 1
CED 회귀

그래프를 켠 초고와 끈 초고를 같은 프롬프트로 뽑아 1만 단어당 일관성 오류를 비교. ConWriter가 유사 기법으로 6,000단어에서 −82%를 보고했으니 그게 상한 기준입니다.

지표 2

LLM 없이 SQL 한 줄로 나와야 합니다. 안 나오면 스키마가 틀린 겁니다.

지표 3
토큰 예산 8,000 이하

챕터 한 편을 쓸 때 컨텍스트에 들어가는 인덱스 크기. 툴 출력 상한 25,000의 3분의 1 안쪽이어야 여유가 있습니다.

정직한 기대치 두 가지

① 구조화 저장소는 전량 독해 대비 토큰 10배 절감에 답변 품질 약 9점 손실입니다(83% vs 92%, 코드베이스 도메인 측정). 소설은 전량 독해가 애초에 불가능하니 이 거래가 유리한 쪽으로 뒤집히지만, “그래프가 읽기보다 무조건 낫다”고 약속하면 안 됩니다.

② 사용자 연구에 따르면 KG 보조 집필의 개선은 행위 중심·구조가 뚜렷한 서사에 집중되고 내면 중심 서사에는 나타나지 않습니다. 미스터리·스릴러가 최적 도메인이고, 제품 주장의 범위도 거기에 한정해야 합니다.

hard/soft 구분이 없으면 원고가 망가집니다

Serena의 rename_memory는 mem: 접두어로 표시된 참조만 갱신합니다. 같은 원리로 — 산문 속 “도영”이라는 이름은 무언가가 그걸 참조로 등록해두지 않았다면 연쇄 대상이 아닙니다. 등록되지 않은 언급을 자동으로 고치려 드는 순간 원고가 망가집니다.

4삼중 시간축

표준 bitemporal(SQL:2011)은 두 축입니다 — 유효 시간과 트랜잭션 시간. 소설은 세 축이 필요합니다.

덮어쓰기 금지의 실증 근거

DToM-Track(arXiv:2603.14646)이 3B~70B 전 모델에서 갱신 후 질문 63.9% vs 갱신 전 질문 27.7%라는 36점 격차를 보고했습니다. 믿음을 in-place로 덮어쓰면 모델은 과거 상태를 구조적으로 복원하지 못합니다. append-only + 구간 스탬프가 선택이 아니라 필수인 이유입니다.

  visible_to ["reader", "character/한도영"]     // V ⊆ {reader} ∪ Characters
  learned_at { "character/서지운": 14 }        // 인물별 인지 시점
  pathway    "direct"                        // direct|observed|told|common
}

// 네 가지 서사 상태가 전부 하나의 술어로 환원됩니다
극적 아이러니   reader ∈ V  ∧  c ∉ V        // 독자만 안다
미스터리       reader ∉ V  ∧  ∃c ∈ V       // 인물만 안다
반전           V를 변경하는 예약 이벤트
연속성 버그    c ∉ V 인데 c가 그 사실을 발화  ← 자동 검출

원 논문(ReverieMem)의 가시성 집합은 인물만 포함합니다. 여기에 reader를 원소로 추가한 것이 이 설계의 확장이고, 그 덕에 극적 아이러니와 미스터리가 같은 술어의 두 경우가 됩니다. 원 논문은 이 구조로 지식 경계 충실도 73.3점(+34.6), 보이지 않는 사실 거부 정확도 81.2%를 기록했습니다.

동일 논문의 ablation 경고

인물별 경험 인덱스(episodic)와 전역 사실 인덱스(semantic)를 둘 다 유지해야 합니다. 에피소딕을 빼면 회상률은 올라가지만 거부 정확도가 무너지고, 시맨틱을 빼면 정반대로 실패합니다. 하나만 두면 예측 가능한 방향으로 망가집니다.

6복선 — F–T–P 3항 상태기계

대부분의 시스템은 복선을 설정→회수 2항 간선으로 모델링합니다. 그러면 두 가지 서로 다른 버그를 구분할 수 없습니다.

CFPG(UCSD, 2026-01)의 기여는 가운데에 트리거를 낀 3항 구조입니다. 트리거는 “복선이 회수 가능해지기 위해 먼저 일어나야 하는 서사적 선행 조건”이고, 이게 있어야 조기 회수(서스펜스 파괴)와 미회수(논리 붕괴)가 갈립니다.

CFPG의 측정치가 트리거의 값어치를 보여줍니다. 미회수 목록을 프롬프트에 그냥 나열하는 베이스라인 대비, F–T–P 게이트를 쓰면 조기 트리거 235건 → 166건(−29.3%), 연속성 충실도 0.453 → 0.647(+43%), 검출 정확도 58.0% → 69.8%였습니다.

가장 훔칠 만한 한 줄

Elson의 Story Intention Graph(LREC 2012)가 15년 전에 이미 답을 냈습니다 — 모든 해석 노드에 actualization status ∈ {Hypothetical, Actualized, Prevented}를 다는 것. 미회수 복선은 “끝까지 Hypothetical인 노드”이고, LLM 없이 계산되는 쿼리가 됩니다.

7씬 — STRIPS식 전이 계약

씬 노드에 {Pre, Post, Forbid} 세 술어 집합을 답니다. 같은 연산자가 생성 제약이자 검증 술어로 쓰이는 게 핵심입니다.

Scene "scene/A2.C14.S01" {

  post   ["조수 시간표 공개", "도영 알리바이 붕괴"]  // 이 씬이 확립하는 것

ConWriter(arXiv:2608.05169)가 이 구조만으로 6,000단어 기준 일관성 오류 밀도 0.4109 → 0.0728 (−82%)를 냈습니다. 그리고 위반 시 씬 전체 재생성이 아니라 위반 문장만 국소 패치합니다 — 편집 비용이 유계로 유지되는 이유입니다.

여기에 PLOTTER(Findings ACL 2026)의 두 가지 결정론적 불변식을 매 쓰기마다 검사합니다. 둘 다 LLM 호출이 필요 없는 순수 그래프 연산입니다.

  • 인과 합리성 — causes 간선 그래프는 DAG를 유지한다. 순환이 생기면 쓰기를 거부한다.
  • 서사 완결성 — 모든 사건 노드는 시작 노드와 끝 노드 양쪽에서 도달 가능하다. 고립된 사건은 버려진 플롯이다.

WITH RECURSIVE reach(id, path, depth) AS (
  SELECT :start, :start, 0
  UNION ALL
  SELECT e.dst, reach.path || ' → ' || e.dst, reach.depth+1
  FROM edge e JOIN reach ON e.src = reach.id
  WHERE reach.depth < :max_depth
    AND e.tx_to IS NULL                          -- 현재 유효한 간선만
    AND e.hard = 1                               -- soft 간선은 순회 제외
    AND (e.story_from IS NULL OR e.story_from <= :as_of)  -- 챕터 컷오프
    AND instr(reach.path, e.dst) = 0             -- 순환 방지
)
SELECT r.path, n.title FROM reach r JOIN node n ON n.id = r.id
WHERE n.kind IN ('Twist','Reveal') ORDER BY r.depth LIMIT :k;

10.1왜 CRDT를 쓰지 않는가

이유 1
동시성이 작고 비대칭적이다

사람 1명 + 에이전트 1개(스위칭이면 사실상 1개)입니다. 커서 50개짜리 문서가 아닙니다. CRDT의 고전적 이득(오프라인 P2P, 서버 없음, 다수 피어)이 하나도 해당하지 않습니다. Linear도 대부분 last-write-wins를 쓰고 CRDT는 이슈 설명에만 씁니다.

이유 2 · 더 중요
자동 수렴이 잘못된 의미론이다

CRDT의 일은 조용히 수렴하는 것입니다. 이 시스템의 일은 종종 그 반대 — 사람이 “9장에서 카엘이 죽는다”고 했는데 에이전트가 “14장에 카엘이 등장한다”고 했으면 고르지 말고 드러내야 합니다. CRDT는 수렴을 주지 정합성을 주지 않습니다.

이유 3
프로버넌스가 더 어려워진다

문자 단위 CRDT 메타데이터는 “에이전트가 세션 S에서 이 필드 변경을 제안했다”와 다릅니다. 결국 프로버넌스 로그를 그 위에 또 만들게 됩니다.

언제 쓰나
노드 안 장문 텍스트에만, 나중에

인물 소개나 씬 설명처럼 사람이 타이핑하는 동안 에이전트가 같은 문단을 고쳐 쓰는 곳이 CRDT가 값어치를 하는 유일한 자리입니다. Yjs + ProseMirror가 성숙한 경로입니다.

13.6스위칭의 뜻밖의 이득 — A/B 비교가 공짜

같은 설정집·같은 복선 상태에서 두 모델이 같은 챕터를 쓰게 하고 결과를 비교할 수 있습니다. op 로그에 model_id가 이미 들어 있으니 모델별 CED를 그냥 집계하면 됩니다.

SELECT p.model_id,
       COUNT(d.id) * 10000.0 / SUM(s.word_count) AS ced
FROM proposal p
  JOIN op   o ON o.proposal = p.id
  JOIN node s ON s.id = o.target AND s.kind = 'Scene'
  LEFT JOIN diagnostic d ON d.node = s.id
WHERE p.status = 'accepted'
GROUP BY p.model_id;

  • MCP prompts를 진입점으로 쓰지 마세요. Codex 클라이언트에 미구현입니다.
  • freshness 판단을 LLM에게 시키지 마세요. 버전 번호가 명시적으로 라벨링된 과제에서조차 실패합니다 — 추출(LLM)과 선택(결정론)을 분리하면 54% → 82%.
  • 믿음·상태를 in-place로 덮어쓰지 마세요. “그때 그녀는 아직 몰랐다”를 구조적으로 못 쓰게 됩니다.
  • 산문 속 언급을 자동으로 고치지 마세요. soft 간선은 보고만 합니다.
  • 캐스케이드가 canon을 자동 커밋하게 두지 마세요. 항상 제안으로.
  • SKILL.md에 호스트 전용 frontmatter를 넣지 마세요. 엄격 검증기에서 하드 에러입니다.
  • Codex CLI를 포크하지 마세요. 월 900커밋, 안정적 out-of-tree API 없음, 유지되는 포크 사실상 0.

모달 승인 다이얼로그를 쌓지 마세요. 맞춤법 밑줄처럼 항상 보이되 방해하지 않는 인라인 표시 + 묶음 검수 큐가 맞습니다. 제안이 쌓이면 사람은 전부 무시하게 됩니다.

원칙 3
출처를 항상 보여준다

모든 값 옆에 누가 언제 왜가 붙습니다 — 사람 / 에이전트 / 캐스케이드. 특히 사람의 편집과 캐스케이드 파생 편집을 시각적으로 구분하는 것이 핵심이고, 이건 공짜로 안 나옵니다.

원칙 4
원문으로 가는 길을 막지 않는다

모든 노드에서 근거 원문 조각으로 한 번에 갈 수 있어야 합니다. 요약이 최종 진실이 아니라 색인이라는 것을 UI가 계속 상기시켜야 합니다.

3.2복선 보드

상태별 4열 칸반 — hypothetical / eligible / actualized / prevented. 카드마다 F · T · P 세 줄과 측정값(S-Eff, Δ-Coh, 부채)이 붙습니다.

열색의미주의 신호
hypothetical위험심겼지만 트리거 미정원고가 끝나가는데 남아 있으면 방치된 복선
eligible대기트리거 발화, 회수 가능오래 대기하면 독자가 잊음
actualized완료회수됨S-Eff가 높으면 너무 티났던 것
prevented중립의도적 폐기 (레드헤링)—

이 화면이 제품의 차별점을 눈으로 보여주는 곳입니다. 다른 도구에는 이 화면이 없습니다.

3.3이중 시간축

가로축은 독자에게 드러난 순서(discourse), 세로 위치는 작중 실제 시간(story). 선이 단조 증가하면 시간순 서술이고, 아래로 꺾인 지점이 회상입니다.

이 꺾임은 작가가 “여기는 회상”이라고 태그해서 나오는 게 아니라 story_from < reveal_at인 노드를 그대로 그린 것입니다 — 두 필드의 불일치가 곧 그림입니다.

7내보내기

  • JSON Canvas(Obsidian) — 뷰 내보내기용으로만. 임의 메타데이터를 노드에 못 붙이고 타입 간선도 없어서 진실의 원천으로는 절대 쓸 수 없지만, 부분 뷰를 Obsidian에서 열어보게 하는 용도로는 충분합니다.
  • Arcweave JSON — 씬 플로우 계층의 상호운용 대상. 상용 서사 도구 중 유일하게 공개·문서화된 포맷입니다.
  • SVG / PNG — 복선 보드와 이중 시간축은 그대로 이미지로 뽑을 수 있어야 합니다. 기획 회의에서 쓰이는 화면입니다.

8접근성과 반응형

  • 라이트/다크 자동 대응 — 토큰 수준에서 정의. 세 상태(명시적 light / 명시적 dark / 시스템)를 모두 처리합니다.
  • 키보드 — ⌘K 옴니 검색, Tab 노드 순회, Esc 선택 해제. 모든 포커스에 가시적 링.
  • prefers-reduced-motion — 캔버스 전환 애니메이션 제거.
  • 좁은 화면 — 1100px 미만에서 레일과 인스펙터를 접고 캔버스만. 복선 보드와 검수 큐는 단일 열로.
  • 색에만 의존하지 않기 — 간선 종류는 색 + 선 스타일 둘 다로 구분합니다. 진단 심각도는 색 + 아이콘.
