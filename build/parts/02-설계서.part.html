과설계 경고

Logseq가 유사한 태그–클래스–다중상속 데이터 모델을 프로덕션에 올리는 데 3년이 걸렸고 아직 데이터 손실 경고를 달고 있습니다. 노드 타입은 20개를 넘기지 마세요. 위 16개면 충분하고, 진짜 표현력은 타입 개수가 아니라 간선 타입과 태그에서 나옵니다. P0에서는 6개만 씁니다(개발계획 §P0).

3간선 카탈로그 — hard와 soft

간선은 두 부류입니다. hard는 기계가 갱신할 수 있고 리네임·삭제 시 연쇄합니다. soft는 산문 속 언급이라 보고만 하고 절대 자동 편집하지 않습니다.

간선도 노드와 같은 삼중 시간축을 갖습니다. “한도영이 서지운에게 적대적” 같은 관계는 언제부터 언제까지 참인지가 본질이라, 간선을 덮어쓰면 “그때는 아직 우호적이었다”를 쓸 수 없게 됩니다.

hard/soft 구분이 없으면 원고가 망가집니다

Serena의 rename_memory는 mem: 접두어로 표시된 참조만 갱신합니다. 같은 원리로 — 산문 속 “도영”이라는 이름은 무언가가 그걸 참조로 등록해두지 않았다면 연쇄 대상이 아닙니다. 등록되지 않은 언급을 자동으로 고치려 드는 순간 원고가 망가집니다.

4삼중 시간축

표준 bitemporal(SQL:2011)은 두 축입니다 — 유효 시간과 트랜잭션 시간. 소설은 세 축이 필요합니다.

덮어쓰기 금지의 실증 근거

DToM-Track(arXiv:2603.14646)이 3B~70B 전 모델에서 갱신 후 질문 63.9% vs 갱신 전 질문 27.7%라는 36점 격차를 보고했습니다. 믿음을 in-place로 덮어쓰면 모델은 과거 상태를 구조적으로 복원하지 못합니다. append-only + 구간 스탬프가 선택이 아니라 필수인 이유입니다.

5가시성 — 누가 무엇을 언제 아는가

이 프로젝트에서 가장 가치가 높은 단일 필드입니다.

Fact {
  subject    "character/한도영"
  predicate  "was_at"
  object     "location/폐선착장"
  cause      "만조를 피하려고"
  visible_to ["reader", "character/한도영"]     // V ⊆ {reader} ∪ Characters
  learned_at { "character/서지운": 14 }        // 인물별 인지 시점
  pathway    "direct"                        // direct|observed|told|common
}

// 네 가지 서사 상태가 전부 하나의 술어로 환원됩니다
극적 아이러니   reader ∈ V  ∧  c ∉ V        // 독자만 안다
미스터리       reader ∉ V  ∧  ∃c ∈ V       // 인물만 안다
반전           V를 변경하는 예약 이벤트
연속성 버그    c ∉ V 인데 c가 그 사실을 발화  ← 자동 검출

원 논문(ReverieMem)의 가시성 집합은 인물만 포함합니다. 여기에 reader를 원소로 추가한 것이 이 설계의 확장이고, 그 덕에 극적 아이러니와 미스터리가 같은 술어의 두 경우가 됩니다. 원 논문은 이 구조로 지식 경계 충실도 73.3점(+34.6), 보이지 않는 사실 거부 정확도 81.2%를 기록했습니다.

동일 논문의 ablation 경고

인물별 경험 인덱스(episodic)와 전역 사실 인덱스(semantic)를 둘 다 유지해야 합니다. 에피소딕을 빼면 회상률은 올라가지만 거부 정확도가 무너지고, 시맨틱을 빼면 정반대로 실패합니다. 하나만 두면 예측 가능한 방향으로 망가집니다.

6복선 — F–T–P 3항 상태기계

대부분의 시스템은 복선을 설정→회수 2항 간선으로 모델링합니다. 그러면 두 가지 서로 다른 버그를 구분할 수 없습니다.

CFPG(UCSD, 2026-01)의 기여는 가운데에 트리거를 낀 3항 구조입니다. 트리거는 “복선이 회수 가능해지기 위해 먼저 일어나야 하는 서사적 선행 조건”이고, 이게 있어야 조기 회수(서스펜스 파괴)와 미회수(논리 붕괴)가 갈립니다.

CFPG의 측정치가 트리거의 값어치를 보여줍니다. 미회수 목록을 프롬프트에 그냥 나열하는 베이스라인 대비, F–T–P 게이트를 쓰면 조기 트리거 235건 → 166건(−29.3%), 연속성 충실도 0.453 → 0.647(+43%), 검출 정확도 58.0% → 69.8%였습니다.

가장 훔칠 만한 한 줄

Elson의 Story Intention Graph(LREC 2012)가 15년 전에 이미 답을 냈습니다 — 모든 해석 노드에 actualization status ∈ {Hypothetical, Actualized, Prevented}를 다는 것. 미회수 복선은 “끝까지 Hypothetical인 노드”이고, LLM 없이 계산되는 쿼리가 됩니다.

7씬 — STRIPS식 전이 계약

씬 노드에 {Pre, Post, Forbid} 세 술어 집합을 답니다. 같은 연산자가 생성 제약이자 검증 술어로 쓰이는 게 핵심입니다.

Scene "scene/A2.C14.S01" {
  pre    ["장갑 젖음 확립", "만조 고립 규칙 유효"]   // 참이 아니면 이 씬은 못 씀
  post   ["조수 시간표 공개", "도영 알리바이 붕괴"]  // 이 씬이 확립하는 것
  forbid ["진범 직접 명시"]                        // 여기서 위반하면 안 되는 것
}

// 실행 가능성 판정 — LLM 없이
feasible(s) ⟺ ∀c ∈ Pre(s) : M ⊨ c
// 커밋 후 기대 상태
M' = Apply(M, Post(s))

ConWriter(arXiv:2608.05169)가 이 구조만으로 6,000단어 기준 일관성 오류 밀도 0.4109 → 0.0728 (−82%)를 냈습니다. 그리고 위반 시 씬 전체 재생성이 아니라 위반 문장만 국소 패치합니다 — 편집 비용이 유계로 유지되는 이유입니다.

여기에 PLOTTER(Findings ACL 2026)의 두 가지 결정론적 불변식을 매 쓰기마다 검사합니다. 둘 다 LLM 호출이 필요 없는 순수 그래프 연산입니다.

  • 인과 합리성 — causes 간선 그래프는 DAG를 유지한다. 순환이 생기면 쓰기를 거부한다.
  • 서사 완결성 — 모든 사건 노드는 시작 노드와 끝 노드 양쪽에서 도달 가능하다. 고립된 사건은 버려진 플롯이다.

8SQL 스키마

SQLite 단일 파일. 그래프 DB를 쓰지 않는 이유는 기술 스택 §거부한 선택지에 있습니다. 전체 DDL은 spec/schema.sql이고, 아래는 핵심만 발췌한 것입니다.

spec/schema.sql (발췌)
CREATE TABLE node (
  id            TEXT PRIMARY KEY,          -- "character/한도영"
  kind          TEXT NOT NULL,
  title         TEXT NOT NULL,
  summary       TEXT,                       -- hover 등가물, 1줄
  props         TEXT NOT NULL DEFAULT '{}', -- JSON
  story_from    INTEGER, story_to INTEGER,   -- 작중 시간
  reveal_at     INTEGER,                    -- 독자 인지 시점
  tx_from       TEXT NOT NULL, tx_to TEXT,   -- NULL = 현재 유효
  origin        TEXT NOT NULL,              -- human | agent | cascade
  locked        INTEGER NOT NULL DEFAULT 0,
  rev           INTEGER NOT NULL DEFAULT 1,
  cid           TEXT NOT NULL,
  CHECK (story_to IS NULL OR story_to >= story_from)
);
CREATE INDEX ix_node_kind   ON node(kind, tx_to);
CREATE INDEX ix_node_story  ON node(story_from, story_to);
CREATE INDEX ix_node_reveal ON node(reveal_at);

CREATE TABLE edge (
  id            INTEGER PRIMARY KEY,
  src           TEXT NOT NULL REFERENCES node(id),
  dst           TEXT NOT NULL REFERENCES node(id),
  rel           TEXT NOT NULL,              -- plants | causes | owns …
  hard          INTEGER NOT NULL DEFAULT 1, -- 0 = soft(산문 언급)
  story_from    INTEGER, story_to INTEGER,
  tx_from       TEXT NOT NULL, tx_to TEXT,
  origin        TEXT NOT NULL,
  confidence    REAL DEFAULT 1.0
);
CREATE INDEX ix_edge_out ON edge(src, rel, tx_to);
CREATE INDEX ix_edge_in  ON edge(dst, rel, tx_to);  -- ★ 역방향이 핵심

-- 다중 상속
CREATE TABLE tag        (name TEXT PRIMARY KEY, schema TEXT);
CREATE TABLE tag_extends(child TEXT, parent TEXT, PRIMARY KEY(child,parent));
CREATE TABLE node_tag   (node TEXT, tag TEXT, PRIMARY KEY(node,tag));
CREATE TABLE feature    (node TEXT, name TEXT, data TEXT, PRIMARY KEY(node,name));

-- 가시성 · 근거 · 편집 로그는 spec/schema.sql 참조
CREATE VIRTUAL TABLE node_fts USING fts5(id, title, aliases, summary, body);
CREATE VIRTUAL TABLE node_vec USING vec0(id TEXT PRIMARY KEY, emb float[1024]);
순회 — 재귀 CTE · “이 소품이 어떤 반전까지 이어지는가”
WITH RECURSIVE reach(id, path, depth) AS (
  SELECT :start, :start, 0
  UNION ALL
  SELECT e.dst, reach.path || ' → ' || e.dst, reach.depth+1
  FROM edge e JOIN reach ON e.src = reach.id
  WHERE reach.depth < :max_depth
    AND e.tx_to IS NULL                          -- 현재 유효한 간선만
    AND e.hard = 1                               -- soft 간선은 순회 제외
    AND (e.story_from IS NULL OR e.story_from <= :as_of)  -- 챕터 컷오프
    AND instr(reach.path, e.dst) = 0             -- 순환 방지
)
SELECT r.path, n.title FROM reach r JOIN node n ON n.id = r.id
WHERE n.kind IN ('Twist','Reveal') ORDER BY r.depth LIMIT :k;

find(q: string, kind?: string[], tag?: string[], as_of?: int,
     mode: "lexical"|"semantic"|"hybrid"="hybrid", limit: int=20) → [{ id, kind, title, summary, score }]

BM25를 반드시 병행합니다 — 특성화 연구에서 BM25 단독이 macro 정확도 55.8%로 구조화 시스템들을 앞섰습니다. 공짜 베이스라인을 버릴 이유가 없습니다.

9.3B군 · 읽기

getread노드 상세
get(ref: string|string[], include: "brief"|"full"|"body"="brief", as_of?: int) → Node[]

include="body"면 depth를 강제로 0으로 낮춥니다. 한 노드의 전문이든 여러 노드의 개요든, 둘을 동시에 주지 않습니다. as_of는 챕터 컷오프 — n+1장 작업 중에 n장 초과 정보가 새는 것을 서버가 막습니다.

refsread역방향 간선 — 가장 많이 쓰이게 될 툴
refs(ref: string, dir: "in"|"out"|"both"="in", rel?: string[],
     include_soft: bool=false, as_of?: int) → [{ rel, id, title, hard, story_range }]

“이걸 가리키는 게 뭐냐” — find_referencing_symbols 등가물. 역방향 간선을 답할 수 없으면 그래프가 아니라 문서 저장소입니다.

traceread두 노드 사이 경로
trace(from: string, to?: string, via?: string[], max_depth: int=5, k: int=5) → [{ path[], rels[], depth }]

“이 소품이 이 반전까지 어떻게 이어지나” — 소설에서 가장 흥미로운 질의입니다. to를 비우면 도달 가능한 서사 장치를 거리순으로 반환합니다.

neighborhoodread질의 조건부 이웃 확장 — 0.358 대 0.898을 가른 메커니즘
neighborhood(intent: string, anchors?: string[], as_of?: int,
             budget_tokens: int=4000) → { packet[], used_tokens, dropped }

NWM의 검색 파이프라인 그대로 — 챕터 컷오프 → BM25+dense를 RRF로 융합해 시드 랭킹 → 각 앵커의 1-hop 타입 이웃 확장 → 예산으로 절단. dropped를 반드시 반환해 무엇이 잘렸는지 모델이 알게 합니다.

9.4C군 · 진단

checkread연속성 진단 — 노드 단위로도, 범위로도
check(scope: ref|"book", rules?: string[], severity?: "error"|"warn"|"info")
  → [{ rule, severity, nodes[], evidence[], message }]

규칙 ID는 ConStory-Bench의 5범주 19서브타입을 그대로 씁니다 — 전체 목록은 spec/rules.json. LSP의 publishDiagnostics처럼 노드에 붙어 있어야 합니다. 배치 리포트가 아니라 편집 중에 걸려야 의미가 있습니다.

promisesread복선 부채 조회
promises(status?: "hypothetical"|"eligible"|"actualized"|"prevented"[],
         as_of?: int, sort: "debt"|"age"|"s_eff"="debt") → [{ id, F, T, P, status, debt, s_eff, delta_coh }]

전용 툴로 뺀 이유는 이게 제품의 차별점이고, 에이전트가 매 씬을 쓰기 전에 호출해야 하는 툴이기 때문입니다. status="eligible"인 것만 컨텍스트에 주입하는 게 CFPG의 게이트입니다.

impactread읽기 전용 캐스케이드 프리뷰
impact(ref: string, change: { field, to }, max_depth: int=3)
  → { affected[], broken_rules[], est_cost_tokens, cycle_detected }

“이걸 바꾸면 뭐가 깨지나” — LSP의 prepareRename과 codanna의 analyze_impact에 해당. 연쇄 편집은 반드시 impact → propose → check 3단으로 흐릅니다.

9.5D군 · 쓰기

proposewrite변경 제안 — 원자적
propose(ops: Op[], read_set: [{ node, rev }], rationale: string, session_id: string)
  → { proposal_id, status: "auto_accepted"|"queued"|"conflict",
      conflicts?[], pending_overlap?[] }

Op = { verb: "ADD"|"UPDATE"|"INVALIDATE"|"LINK"|"UNLINK",
       target, field?, from?, to?, basis_rev? }

read_set이 이 설계 전체에서 가장 값어치 있는 한 필드입니다 — 충돌 판정 기준, 프로버넌스 증거, 도미노 전파 의존 간선이 전부 여기서 나옵니다. from을 요구하는 이유는 조건부 op를 만들기 위해서입니다. to만 있는 op는 last-writer-wins 지뢰입니다. 빈 read_set은 거부합니다.

commitwrite제안 확정
commit(proposal_id: string, mode: "apply"|"dry_run"="apply")
  → { applied[], rejected[], cascade_id?, diagnostics[] }

정책을 통과한 제안만 자동 적용됩니다(§10.4). 나머지는 queued로 남아 사람의 검수 큐로 갑니다. 커밋 직후 영향받은 부분그래프에만 check를 재실행합니다.

ingestwrite원고 → 그래프 증분 추출
ingest(chapter: string, mode: "extract"|"reindex"="extract")
  → { proposal_id, extracted: { nodes, edges, facts }, invalidated[] }

NWM의 Publish 흐름 — 확정된 산문만 기록하고, 챕터를 수정 재발행하면 그 지점 이후의 파생 간선을 무효화합니다. 추출 결과도 제안으로 들어옵니다. 자동 커밋하지 않습니다.

leasewrite작업 구역 선점 — 다중 에이전트에서만 필요
lease(mode: "acquire"|"release"|"list", scope?: string,
      ttl_sec?: int=900, session_id: string, note?: string)
  → { lease_id, scope, holder, expires_at, conflicts?[] }

스위칭(번갈아 사용) 운용에서는 필요 없습니다. 두 에이전트를 동시에 붙일 때만 씁니다. TTL이 필수인 이유는 세션이 죽어도 자동 해제되어야 하기 때문입니다. 리스는 권고이지 잠금이 아닙니다.

queryread탈출 해치 — 읽기 전용 SQL
query(sql: string, params?: object, limit: int=200) → { columns[], rows[][], truncated }

codebase-memory에서 가장 많이 쓰이는 툴이 14개 편의 툴이 아니라 이 raw 질의였습니다. 에이전트는 질의를 잘 씁니다 — 모든 걸 손으로 빚은 툴로 강제하지 마세요. 읽기 전용 커넥션으로 열고, graph_schema가 스키마를 알려주므로 모델이 스스로 질의를 만들 수 있습니다.

9.8보안과 운영

  • stdio 전용. confused deputy, 토큰 패스스루, SSRF, 상태 핸들 탈취, OAuth URL 검증 — MCP 스펙 보안 절의 다섯 공격군이 전부 HTTP 전용이라 통째로 사라집니다.
  • readOnlyHint를 게이트로 신뢰하지 마세요. MCP 공식 블로그가 명시합니다 — “클라이언트는 힌트를 신뢰하지 않아야 한다. 신뢰할 수 없는 서버는 readOnlyHint: true라고 주장하고도 파일을 지울 수 있다.” 게이트는 서버 툴 구현부에 둡니다.
  • 입력 검증과 rate limit은 스펙의 MUST입니다. 경로 탈출 차단, 호출 빈도 제한 — 폭주하는 에이전트의 그래프 순회는 실제 실패 모드입니다.
  • execute_shell_command 류는 만들지 않습니다. 소설 설정집이 셸을 소유할 이유가 없습니다.
  • 로컬 stdio는 기본적으로 신 리비전으로 협상되지 않습니다. 신 리비전 전용 기능을 필수 경로에 두지 말고 SDK 호환 계층에 맡기세요. 대신 공짜인 건 지금 지킵니다 — tools/list 결정적 정렬(프롬프트 캐시 적중률), 세션 중 툴 목록 불변.

10버전 관리 — op 로그와 충돌 판정

사람과 에이전트가 같은 그래프를 쓰는 문제. 결론부터 — CRDT를 쓰지 않습니다.

10.1왜 CRDT를 쓰지 않는가

이유 1
동시성이 작고 비대칭적이다

사람 1명 + 에이전트 1개(스위칭이면 사실상 1개)입니다. 커서 50개짜리 문서가 아닙니다. CRDT의 고전적 이득(오프라인 P2P, 서버 없음, 다수 피어)이 하나도 해당하지 않습니다. Linear도 대부분 last-write-wins를 쓰고 CRDT는 이슈 설명에만 씁니다.

이유 2 · 더 중요
자동 수렴이 잘못된 의미론이다

CRDT의 일은 조용히 수렴하는 것입니다. 이 시스템의 일은 종종 그 반대 — 사람이 “9장에서 카엘이 죽는다”고 했는데 에이전트가 “14장에 카엘이 등장한다”고 했으면 고르지 말고 드러내야 합니다. CRDT는 수렴을 주지 정합성을 주지 않습니다.

이유 3
프로버넌스가 더 어려워진다

문자 단위 CRDT 메타데이터는 “에이전트가 세션 S에서 이 필드 변경을 제안했다”와 다릅니다. 결국 프로버넌스 로그를 그 위에 또 만들게 됩니다.

언제 쓰나
노드 안 장문 텍스트에만, 나중에

인물 소개나 씬 설명처럼 사람이 타이핑하는 동안 에이전트가 같은 문단을 고쳐 쓰는 곳이 CRDT가 값어치를 하는 유일한 자리입니다. Yjs + ProseMirror가 성숙한 경로입니다.

라이브러리 현황 (2026-08 확인)

Yjs 14가 예고한 “changesets + attributions”는 정확히 이 시스템의 요구사항이지만 2025-12부터 beta에 머물러 있고 stable은 13.6.32이며 같은 릴리스에서 move가 제거됐습니다. Loro 1.14.x는 Kleppmann의 검증된 move 알고리즘 기반 Tree/MovableList를 가진 유일한 선택지지만 생태계가 얇습니다. 리스트 순서 문제는 지금은 fractional indexing으로 해결하세요 — 라이브러리와 무관하고 오늘 동작합니다.

13.6스위칭의 뜻밖의 이득 — A/B 비교가 공짜

같은 설정집·같은 복선 상태에서 두 모델이 같은 챕터를 쓰게 하고 결과를 비교할 수 있습니다. op 로그에 model_id가 이미 들어 있으니 모델별 CED를 그냥 집계하면 됩니다.

SELECT p.model_id,
       COUNT(d.id) * 10000.0 / SUM(s.word_count) AS ced
FROM proposal p
  JOIN op   o ON o.proposal = p.id
  JOIN node s ON s.id = o.target AND s.kind = 'Scene'
  LEFT JOIN diagnostic d ON d.node = s.id
WHERE p.status = 'accepted'
GROUP BY p.model_id;

개발계획서의 회귀 스위트가 모델 선택 실험 도구로도 그대로 쓰입니다. 별도로 만들 게 없습니다.
